# Visual comparison against the approved references

TASKS 22.3. Two references in `references/approved-ui/` were compared against the
built screens: `skill-tree.png` and `node-detail.png`.

This is a review, so it records what differs — including the parts that are worse
than the reference. Where a difference was cheap to fix correctly it was fixed and
is marked **fixed**; where it would need a design decision or new product work it
is left as a finding with the reasoning.

Screenshots of every screen at every required viewport are regenerated by
`e2e/responsive.e2e.ts` into `test-results/responsive/` on each run.

---

## 1. Skill tree map — `skill-tree.png`

### Proportions — **the significant difference, now fixed**

The reference shows four or five columns of large hexagons with the tree running
off the edge of the frame. You are meant to *pan*.

The build opened on the whole tree fitted to the canvas. The map frame is 2450
units wide and the canvas is about 590px in the desktop three-column layout, so a
58-unit hexagon rendered at roughly 14px — the icons inside were gone and the
drawing was a grey mesh. It was technically correct and practically unreadable.

**Fixed.** `INITIAL_VIEWPORT` in `components/skill-tree/skill-tree-geometry.ts`
opens on 1100 units, which puts a hexagon near 30px, with `y` chosen so the Origin
— the node every path grows from, at y ≈ 1290 — is the first thing on screen. `Fit`
still gives the overview.

Making the opening viewport smaller than the drawing immediately produced a
*second* problem, and it is recorded here because it is a trap: `getBoundingClientRect`
on SVG geometry reports where a shape *is*, not where it is *visible*, so every
path running past the viewBox measured as overflowing the page. The `<svg>` crops
it. The responsive audit now exempts descendants of a clipping `<svg>`, scoped
narrowly so that `overflow: hidden` on a `Card` does not get the same exemption.

### Spacing

Matches. The branch rail, canvas and detail panel sit on the same gutter, and the
rail's card edge aligns with the canvas card edge and the detail card edge.

### Typography

The wordmark, nav, section labels and body copy match the reference's scale and
contrast. The tier axis on the right (Mastery / Advanced / Intermediate /
Foundation / Roots) is **noticeably smaller and more cramped** than the reference,
where the labels are comfortably legible with a dotted rule running beside them.
Still a finding.

### Component hierarchy

Matches well. Icon plus label plus `n/m` count per branch, the active branch
raised with a stronger border — this is the clearest structural agreement between
the reference and the build.

### Colour use

Agrees with the design system's rules rather than with the reference's *data*: the
reference is bright with unlocked nodes in orange, green and blue, and the build
is uniformly grey. That is correct here — the screenshot was taken with 22 of 22
skill points unspent and no evidence ingested, so every node is locked and locking
is monochrome by design. The colour vocabulary is present in the branch icons and
in the `Unlocked` badge; there was simply nothing unlocked to show.

### Animation

Cannot be compared from a still. The build has an unlock reveal, a hover state and
a branch-filter transition, all on `--motion-*` tokens with `motion-reduce`
alternatives; the reference is also a still.

### Responsive behaviour

Covered by the audit rather than by eye. The branch rail becomes a horizontal
scroller below `md` and a column above it, which is the right answer at both ends.
The rail's buttons were 38px tall on touch screens — a filter chip under a thumb is
a target, not a dense desktop control — and are now 44px below `lg`.

**Not implemented:** the reference's minimap, bottom-left. The zoom cluster
(`+` / `−` / `Fit`) is the only way to navigate the map, and the minimap is how the
reference supplements it. Genuinely missing, and it is the largest known gap.

## 2. Node detail — `node-detail.png`

The build renders node detail as a persistent third column rather than the
reference's full-width overlay reached by "← Back to Tree". That is a deliberate
layout decision taken earlier: keeping the map visible while reading a node means
clicking a related node does not lose your place. It diverges from the reference
and is better for the task, but it is a divergence.

### Present and agreeing

- Identity: icon, name, tier, unlock state
- Description
- An evidence progress bar with a count
- Requirements, rendered as the cheapest path to unlock when prerequisites are
  unmet — a better answer than the reference's flat checklist, because it tells you
  what to do next rather than only what is missing
- Rewards
- **Learn — N points**, the primary unlock action, with Learn/Refund and reasons

### Findings

1. **No Related Nodes panel.** The reference shows connected nodes with `Locked`
   and `Current` states, which is how a reader understands where a node sits in
   the graph without panning back to the map. The build has the graph, but only on
   the map. Missing.

2. **No repository-level evidence.** This is the biggest content gap. The
   reference's Evidence panel lists actual repositories — `plvtolee/data-lib`,
   "Implemented module system", 342 stars — so the progress bar is *substantiated*
   by the thing that earned it. The build shows one generic "Evidence source" line
   per node. A progress bar whose basis is invisible is a progress bar the reader
   has to take on trust. This is the single most valuable missing feature in the
   comparison, and it needs the evidence model exposed per node rather than only
   aggregated.

3. **The node name is not a hero.** In the reference the title is `display`-scale,
   under a large hexagon. In the build it is `heading` in a narrow column. With a
   third of the screen width instead of the full frame, that is a reasonable
   adaptation, but the panel is quieter than the reference intends.

4. **Meta is caption text, not chips.** Branch, tier and rarity are one caption
   line ("Roots · Core · 0 points") where the reference has three discrete chips.
   The chips are what let a reader scan one attribute without reading the line.

5. **The reference's `Track Progress` CTA is not mirrored.** The build has a real
   action (`Learn`) where the reference has a demo affordance, so this is a case
   where following the reference would be *worse*. Noted and dismissed.

## 3. Screens with no reference

`/`, `/preview`, `/profile`, `/achievements`, `/quests`, `/shop`, `/customization`
and `/leaderboard` have no approved reference to compare against. They were
reviewed against the design system (`docs/DESIGN_SYSTEM.md`) and the design tokens
instead, which is a weaker guarantee — a reference is a decision someone made, and
tokens only say what is permitted.

What that review did find is in the responsive audit: nine controls below the 44px
touch minimum, a 414px element running off a 375px screen, and a 2-line README.

---

## Summary

| reference | agreement | material findings |
| --- | --- | --- |
| `skill-tree.png` | good after the viewport fix | minimap missing; tier labels cramped |
| `node-detail.png` | partial | no Related Nodes; no repository-level evidence; title not a hero; meta not chips |

Two of the four skill-tree findings and one of the four node-detail findings were
fixed in this phase. The rest are recorded rather than quietly dropped, because
each needs either a design decision or work on the evidence model that is larger
than a polish pass.

The repository-level evidence gap (2) is the one worth doing next: it is the
difference between a progression screen that is true and one that is merely
consistent.
